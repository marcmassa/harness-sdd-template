# Design — add-user-api

> Technical decisions to implement FEAT-EX-001. This example uses pseudo-code and language-agnostic file paths. In a real project, replace these with your actual stack (Python, Go, TypeScript, Java, etc.).

---

## Summary

Add a `POST /users` registration endpoint to the existing REST API. The endpoint validates input, persists a new user record with a hashed password, and enqueues a welcome notification. The notification step is fire-and-forget — a failure there does not block registration.

## Signatures and Structures

### HTTP Layer

```
POST /users
Content-Type: application/json

Request body:
  { "email": string, "password": string }

Responses:
  201 Created     → { "id": uuid, "email": string, "created_at": iso8601 }
  409 Conflict    → { "error": "email_taken" }
  422 Unprocessable → { "errors": [{ "field": string, "reason": string }] }
```

### Service Interface

```
function register_user(email: string, password: string) -> UserRecord | Error
  1. validate_input(email, password) → raises ValidationError
  2. check_uniqueness(email) → raises DuplicateEmailError
  3. hash = hash_password(password)
  4. user = repository.create({ email, password_hash: hash })
  5. try: notifications.enqueue_welcome(user.id)
     catch NotificationError: log.warn("enqueue failed", user_id=user.id)
  6. return user
```

### Data Model

```
User {
  id:            uuid (generated by persistence layer)
  email:         string, unique, indexed
  password_hash: string
  created_at:    timestamp (set by persistence layer)
}
```

---

## Algorithm / Flow

```
1. Receive POST /users request
2. Deserialize + validate body against schema (email format, password length)
   → 422 if invalid
3. Query repository for existing email
   → 409 if found
4. Hash password (bcrypt/argon2 with cost factor from config)
5. Persist new user record
6. Enqueue welcome notification (async, failure is non-fatal)
7. Return HTTP 201 with { id, email, created_at }
```

---

## Error Handling

| Condition | Response |
|-----------|----------|
| Invalid email format | HTTP 422, field: email, reason: invalid_format |
| Password shorter than 8 chars | HTTP 422, field: password, reason: too_short |
| Email already registered | HTTP 409, error: email_taken |
| Persistence failure | HTTP 500, log full error stack |
| Notification enqueue failure | HTTP 201 returned, failure logged (non-fatal per R7) |

---

## Discarded Alternative

**Validate uniqueness inside the database constraint only (no application-level check).**

Discarded because:
- A DB unique constraint returns a generic persistence error; surfacing it as HTTP 409 with `email_taken` requires catching and interpreting DB-specific error codes — fragile and driver-dependent.
- Application-level uniqueness check makes the behavior explicit, testable in isolation, and consistent across datastores.
- Race condition risk (two concurrent requests passing the check simultaneously) is accepted: the DB constraint acts as the final guard and a 500 is returned in that rare case, which is a better tradeoff than opaque error mapping.

---

## Risks and Edge Cases

- **Concurrent registration with the same email:** The application-level check is not atomic with the insert. The DB unique constraint handles this; a 500 is returned in the rare race case.
- **Password hashing cost factor:** Too high → slow endpoint; too low → weaker security. Externalize as a config value; default to the library's recommended minimum.
- **Notification queue unavailable at startup:** Enqueue failures are non-fatal per R7, but persistent queue unavailability should surface in a health check endpoint, not silently.
